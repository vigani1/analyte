# Analyzer bridge: independent middleware research

Research cutoff: 15 November 2026. External sources only; existing analyzer plans were not read. No implementation or hardware testing was performed.

## Short summary

**Inferred:** Build a durable, observable store-and-forward service with device-specific protocol state machines, not a stateless format converter. Keep transport receipt, durable acceptance, parsing, application delivery, and clinical acceptance distinct. Preserve source bytes and result history. Answer time-sensitive instrument queries locally when possible, under an explicit order freshness policy.

**Inferred:** Start with compiled drivers behind a small, explicit interface. Let the host own serial/TCP access, persistence, HTTPS delivery, credentials, and audit events. Choose a third-party execution mechanism after testing representative drivers; neither a scripting engine nor WASM automatically supplies a safe clinical driver contract.

**Verified:** Mature engines expose queues, message history, recovery tools, and deployment controls. Instrument middleware additionally handles specimen/test mappings and laboratory workflow. Public vendor brochures establish capabilities, not their internal guarantees. Sources: Rhapsody, [IRIS suspended messages][iris-messages], [Iguana persistence][iguana-persistence], [OIE lifecycle][oie-life], Instrument Manager.

Labels throughout: **Verified** means explicitly read in a cited source, including a report's description of an incident; it does not mean independently reproduced. **Inferred** means a recommendation or interpretation. Evidence strength: **strong** = normative/public technical documentation or direct implementation evidence; **medium** = vendor capability statement or bounded observational study; **weak** = unconfirmed issue/forum report or proposed design. A recent crate release establishes publishing activity, not clinical fitness.

### What established products actually expose

**Verified — Rhapsody:** Its on-premise product separates an engine, graphical IDE and web management console. Communication points and routes feed filters/mappers/JavaScript; an RDK supports extensions. Configurable archives permit edit, resend and reprocess; the console shows message paths, connection/throughput problems and processing logs. Alerts have component thresholds. The IDE generates configuration documentation. This is a vendor capability sheet, not evidence of exactly-once delivery or a particular transaction boundary. Rhapsody

**Inferred — Rhapsody lesson:** Copy the operational separation between configuration and monitoring. Public material reviewed here did not establish its config history semantics, rollback compatibility, storage implementation or engine upgrade procedure; those details remain unverified.

**Verified — InterSystems IRIS / Health Connect:** Productions contain business services, processes and operations. Suspended messages have a dedicated queue and can be resubmitted, edited or discarded. Editing creates a new body while retaining session linkage. Request/response states are separate. Alerts can use retry grace periods. Deployment packages include selected classes/settings, but some dependencies must be added explicitly. The deployment portal creates rollback/log files, disables affected components, imports/compiles, and rolls back compilation failures. [Message management][iris-messages], [concepts][iris-concepts], [alerts][iris-alerts], [deployment][iris-deploy]

**Inferred — IRIS lesson:** Keep connection adapters, workflow interpretation and outbound delivery separate. Export a complete dependency set. Do not assume these exact IRIS guarantees automatically apply to every HealthShare product/version; this research verified the cited interoperability engine documentation.

**Verified — iNTERFACEWARE Iguana:** Channels use source/filter/destination components and Lua Translator logic. Queue-backed processing permits replay from logs; replay behavior depends on where logic is placed. Iguana X distinguishes journal-backed `queue.push` from nonpersistent `message.send`. Iguana 6 exports/imports channels through Git and can update Translator code separately from channel settings. [Structure][iguana-structure], [persistence][iguana-persistence], [replay][iguana-replay], [Git export][iguana-git]

**Inferred — Iguana lesson:** Put recoverable work behind a durable boundary. Version code and connection settings together for validation even when a tool permits independent updates. These sources span Iguana 6 and X; do not assume migration compatibility. Detailed alert delivery, backup and upgrade guarantees were not verified.

**Verified — Mirth Connect:** Indexed excerpts of the published 4.5 guide describe queued messages waiting for dispatch, and error-based alerts with email/channel actions. Advanced metric alerts and escalation are described as an extension. The full PDF exceeded the research browser's size limit; it was not read end to end. Its public repository carries version-specific defect reports. User guide, [repository issues][mirth-issues]

**Verified — Open Integration Engine:** Its channel pipeline includes preprocessing, filters/transformers, destinations and postprocessing. Storage modes affect recovery: Production/Development retain durable processing state; Metadata/Disabled cannot provide equivalent replay. Saved configuration is separate from the deployed definition. Monitoring supports per-message/destination reprocessing and events; alert actions include email or routing to a channel. [Lifecycle][oie-life], [channels][oie-channels], [deployment state][oie-state], [monitoring][oie-monitor], [alerts][oie-alerts]

**Verified — OIE operational trade-off:** One queue thread without rotation preserves order but a failing message blocks later messages. More threads or rotation can change order. Queue retries can continue indefinitely; disk growth therefore remains an operational risk. [Queueing][oie-queue]

**Inferred — Mirth/OIE lesson:** Do not treat a “high performance” storage setting as a harmless tuning change. Use explicit ordering per clinical workflow, not global serialization or unconstrained parallel delivery. Exported configuration needs external review/version control; a saved revision is not proof of what is running.

**Verified — BridgeLink:** This Mirth-derived engine publishes source and release notes. The reviewed notes describe Java/runtime migrations, database schema checks and character-encoding changes, including connectors beginning to honor a charset property they previously ignored. Channel-aware logging is also described. [Source/releases][bridge-releases], [upgrade notes][bridge-docs]

**Inferred — BridgeLink lesson:** A fork's common ancestry does not prove drop-in upgrade or extension compatibility. Pin engine/runtime/extensions, back up configuration and message storage, rehearse migrations with representative data, and validate wire output after upgrading. Documentation reviewed did not establish a complete rollback procedure.

**Verified — Data Innovations Instrument Manager:** Public materials describe a driver library, multi-instrument/LIS connectivity, graphical rules, QC integration and specimen workflows. Its inspection material shows communications trace, loopback testing, system log, specimen event log and audit-trail views. Product/workflow material, inspection guide

**Inferred — Instrument Manager lesson:** Analyzer integration has a device driver and specimen/test mapping layer, not merely transport connectors. Preserve diagnostics searchable by specimen. Exact retry durability, config version history, driver SDK, retention and upgrade behavior were not established from the public material; vendor marketing cannot fill those gaps.

**Verified — Roche vendor middleware:** A public cobas infinity manual describes uni/bidirectional patient, order and result exchange. A cobas liat guide documents infinity edge status including gateway, last connection/workflow and distinct workflow, HTTP and communication errors. These are different products, not a single implementation. Infinity manual, liat/edge guide

**Inferred — deployment pattern:** For this PC-sized bridge, one service plus an embedded durable database and local diagnostics is a reasonable starting point. A central engine cluster, graphical workflow designer, autoverification rules engine or remote plugin marketplace does not follow from these sources. Deployment should drain or record in-flight sessions, preserve pending deliveries, verify configuration, and identify the active software/driver/config versions after restart.

## Common mistakes

1. **Verified report:** OpenELIS bridge issue #26 describes a missing ETX/ETB causing an unbounded frame accumulator, log flooding and possible heap exhaustion. A mock's incorrect ETB constant exposed the problem. The live GitHub API showed the issue closed when checked; closure alone does not prove a released fix. **Inferred:** Bound bytes and time, parse control bytes before character decoding, test malformed streams, and retain the minimized failure corpus. [Issue #26][oe-issue]
2. **Verified report:** Mirth #6440 reports the first tilde disappearing in JSON input; this was an open report, not independently reproduced. **Inferred:** Compare raw and transformed bytes in validation, including separators and escape characters. [Issue #6440][mirth-tilde]
3. **Verified report:** Mirth #6506 reports a Windows 11 installer stalled at extension selection with OpenJDK 25. **Inferred:** Validate a supported installer/runtime matrix, including unattended restart recovery, rather than assuming a newer runtime is compatible. [Issue #6506][mirth-installer]
4. **Verified:** A study of 6,930 paired glucose entries found 3.7% manual discrepancies, with some potentially dangerous errors. **Inferred:** Manual downtime entry needs reconciliation and duplicate handling when automated delivery resumes. It is not a risk-free fallback. [Transcription study][transcription]
5. **Verified:** A 2018 case report describes orders cancelled in the external lab while upstream users still saw active orders; two patients experienced delayed collection. **Inferred:** Transport ACKs must not be displayed as order acceptance; propagate rejection/cancellation and reconcile outstanding work. [Case report][orders-paper]
6. **Verified:** A 2010 case series identifies routing logic, provider records, EHR settings and maintenance as sources of result-delivery disruption. **Inferred:** Validate the final destination and route, not just the bridge's successful POST. [Result-management series][routing-paper]
7. **Verified:** A Pennsylvania safety review classified 69 of 917 reports as system-interface issues and included results not crossing systems and a result autoverified before autodilution. **Inferred:** Preserve workflow state and test dilution/correction paths, not only ordinary numeric results. These report proportions are not population incidence rates. [Safety advisory][pa-safety]
8. **Verified:** SHOT's 2016 near-miss report describes incorrect ABO allocation from interruption of autovalidation and explicitly says that particular case was not an interface error. **Inferred:** Fault injection must extend to interruption/restart and downstream result assignment; do not miscite it as proof of a bridge transport defect. SHOT
9. **Verified anecdote:** A lab forum participant reports communication hiccups leaving Roche results requiring manual entry. This is unconfirmed and model-specific. **Inferred:** During commissioning, demonstrate actual instrument resend behavior rather than relying on a protocol label. [Lab forum][lab-forum]
10. **Inferred:** Other recurring design errors are discarding unknown codes, trimming leading-zero sample IDs, converting every result to a floating-point number, overwriting finals on retransmission, replaying old orders without checking their lifecycle, and logging identifiable payloads in ordinary telemetry. Validation sources below explain why these need explicit cases.

## Standards notes

### CLSI LIS1/LIS01 and LIS2/LIS02: two different layers

**Verified:** CLSI LIS01-A2 (2008) replaces LIS1-A and covers low-level serial and TCP/IP exchange. LIS02-A2 (2004) defines the content of requests, results and demographics; low-level transfer is outside its scope. Both catalog pages mark these editions archived, not actively maintained by consensus review. The former ASTM E1381/E1394 editions are related predecessors, not interchangeable version labels. This research did not verify all normative clauses. CLSI LIS01-A2 and LIS02-A2

**Verified — concrete Roche implementation, not a universal ASTM default:** The e 411 v2.0 manual defines half-duplex sessions; either side can initiate. ENQ establishes, ACK/NAK controls transfer, EOT terminates. Simultaneous ENQs give the analyzer priority, with a one-second instrument delay; busy establishment uses a ten-second wait and six retries. Silence produces a fifteen-second timeout. Frames have up to 240 text bytes, 247 total, frame numbers 1–7 then 0–7, ETB for continuation and ETX for final, plus two ASCII hex checksum digits summing FN through ETB/ETX. Its Q record requests orders and can cancel a query. Elecsys/cobas modes differ in frame/record packing. Manual, B-2, D-2–D-8, E-8 (Roche e 411 Host Interface Manual)

**Verified — additional implementation evidence:** `go-astm` documents 240-byte default text splitting, ETB continuation, ETX final, a fifteen-second send-response timeout and thirty-second receive silence timeout. It is implementation evidence, not a substitute for licensed CLSI requirements. [go-astm][go-astm]

**Inferred:** Implement an explicit sender/receiver state machine with separate establishment, frame-response and receive deadlines; do not use a single generic socket timeout. NAK, repeated frame number, unexpected ENQ/EOT, checksum failure, retry exhaustion and disconnect require defined transitions. Confirm exact retry counting and timeout behavior against each instrument's firmware manual. Do not make one TCP read, one frame, one record and one message synonymous.

**Inferred:** Frame-level ACK durability needs deliberate design. If an instrument will not resend already-ACKed frames after failure, durable partial-session storage may be necessary; alternatively establish an instrument-supported whole-message recovery procedure. A database write for the final message alone does not prove every earlier frame is recoverable. Test disk latency against ACK deadlines.

**Inferred:** At the content layer, retain header/patient/order/result/comment/query/terminator relationships and distinguish a negative order-query response from a connection failure. A Q record is not a result record or a generic database query. Host-query support requires an actual order source and device-specific response grammar.

### HL7 v2 laboratory messages and MLLP

**Verified:** HL7 2.3.1 observation reporting describes patient → order → observation grouping. OBX observation identity and sub-ID matter to replacement/correction behavior. HL7's official observation status table defines `F` final, `P` preliminary, `C` correction replacing final results, and `X` results cannot be obtained for that observation. Other codes include deletion and wrong-result handling. [Chapter 7][hl7-ch7], [official table 0085][hl7-status]

**Inferred:** Keep OBX-11 observation status separate from OBR-25 report/order status and ORC order control. In particular, `X` must not become an unconditional “order cancelled” flag. Preserve predecessor linkage and the original result when applying a correction; do not key replacement on sample ID and test name alone. Agree the identity tuple with the peer, including order, instrument, observation code/system and sub-ID/run.

**Verified:** LAW's HL7 2.5.1 transaction set uses QBP^Q11/RSP^K11 for querying, OML^O33/ORL^O34 for work distribution, and OUL^R22/ACK^R22 for status/results. Its RSP acknowledges the query; AWOS content is distributed via LAB-28. An inconsistent LAB-29 message can require whole-message rejection, not partial acceptance. LAW volume 2b, §§3.27–3.29, Appendix B

**Inferred:** ORU unsolicited results, OUL specimen-oriented results, OML orders, ORL order responses and QBP/RSP queries are message families with version/profile-specific structures. “HL7 support” is insufficient. Never force a 2.3.1 analyzer into a 2.5.1 LAW schema. Record trigger events, optional segments, code systems, acknowledgement modes, charset and accepted extensions per driver.

**Verified:** MLLP wraps payloads with `0B` and `1C 0D`; HL7 ACK fields are distinct from transport framing. Philips integration guide

**Inferred:** Decode a byte stream incrementally: split frames across reads and multiple frames per read are normal TCP conditions. Bound frame size/time and correlate MSA-2 with outbound MSH-10. A TCP connection, MLLP frame, HL7 acceptance ACK, order acceptance and clinical release are different events. Confirm ACK timing and retry policy with the vendor; MLLP itself supplies neither encryption nor business idempotency.

### IHE Laboratory Analytical Workflow (LAW)

**Verified:** The final-text PaLM framework revision 11.0 (2024) defines Analyzer and Analyzer Manager actors and LAB-27 query, LAB-28 broadcast and LAB-29 status change. An Analyzer can support results only; bidirectional support requires both query and broadcast transactions. Options include tray/all queries, dilution, rerun/reflex and additional specimen information. Volume 1, §5

**Verified:** LAW distinguishes analyzer-initiated reruns under the same AWOS with observation sub-IDs from manager-requested reruns generating a new AWOS. Final/corrected status identifies the selected result. LAW scenarios

**Inferred:** Model specimen/container, requested work and analytical runs separately. Preserve dilution factors and whether the returned concentration was already adjusted. A corrected interpretation, retransmission and new physical measurement need different identities. LAW is useful vocabulary even for proprietary drivers; that does not make those drivers LAW conformant.

**Verified:** IHE Gazelle offers Analyzer/Analyzer Manager simulations, query responses, work distribution and result testing. **Inferred:** Use these for a LAW driver if one is built, alongside the real machine; simulator success is not device acceptance. [Gazelle manual][gazelle]

### POCT1-A2

**Verified:** CLSI POCT01-A2 (2006) covers bidirectional device/access-point/data-manager connectivity and supports application policies without defining those policies itself. Siemens' Atellica VTLi specification describes a Device Messaging Layer between device and data manager for results and quality information. This is not simply another name for an HL7/MLLP link. CLSI POCT01, Siemens specification

**Inferred:** Keep it a future protocol driver family if actual devices require it; do not build operator certification or device lockout just because a connectivity standard can carry supporting data.

### Interface validation and laboratory obligations

**Verified:** CAP's publicly accessible 2020 GEN.48500 requires verification before implementation and after changes affecting transmission accuracy, through the first downstream system routinely used by clinicians. Examples include batteries, flags, reference intervals, comments and corrected results. This is an edition-specific source, not proof of the current licensed checklist wording. CAP

**Verified:** The accreditation-body ISO 15189:2022 assessment checklist reproduces §7.6 expectations: supplier validation, laboratory functional verification before introduction, authorized/documented/validated changes, and functioning interfaces. The licensed ISO text was not read in full. PJLA checklist

**Verified:** CLIA §493.1291 requires reliable, timely transmission to the final reporting destination; §493.1291(k) requires prompt correction/notification and retention of original and corrected reports. CMS's revised 2025 guidance addresses downtime and delayed-result reporting. These are US laboratory obligations, not an automatic certification scheme for an open-source bridge. Regulation, CMS guidance

**Inferred:** Maintain a commissioning evidence pack: agreed mapping and device settings; synthetic/de-identified inputs; expected clinical outputs; observed final-screen outputs; ACK/error behavior; correction/rerun/partial/QC cases; downtime and restart recovery; approvals; and exact version/config checksums. Repeat affected cases after firmware, mapping, driver, bridge, receiving app or runtime changes. Responsibility belongs to the deploying laboratory together with suppliers, not a parser library alone.

### GDPR and EU device qualification

**Verified:** GDPR treats health data as a special category. Articles 5 and 9 address purpose/minimization/storage limitation and permitted processing; Articles 25, 28 and 32 address design, processors and security; international transfers have additional conditions. It does not prescribe one universal bridge retention period. [GDPR][gdpr]

**Inferred:** Determine controller/processor roles, legal bases, hosting/support locations and retention with each deployment. Device raw traces, local spool, backups and identifiers remain in scope even if the cloud connection uses TLS. Use OS access controls and disk encryption, restrict support exports, and keep credentials outside ordinary config exports. Do not assume patient consent is the only legal basis or that a sample barcode is anonymous.

**Verified:** MDCG 2019-11 rev.1 (June 2025), §3.3 and Annex I, distinguishes communication/storage from medical-device functions. LIS/WAM are not devices in themselves; modules can qualify independently. Software driving/influencing a device or qualifying as an accessory is considered before the simple communication branch. §3.4 addresses IVD qualification. Current guidance

**Inferred:** A bridge limited to faithful transfer may fall outside MDSW qualification, but sending commands/worklists, selecting reruns or controlling QC needs intended-purpose analysis. Neither “open source” nor “only transfers data” settles accessory/driving status. Write a precise intended-purpose statement and review actual functions before making an exclusion claim. Basic unit conversion alone is not proof of device status; the guidance gives representation-changing operations as non-IVD examples. This research is not a product classification determination.

### Third-party driver hosting decision

**Inferred — contract first:** Let a driver consume bounded bytes/events, maintain connection-local protocol state, emit validated observations/query requests and request bounded writes. The host supplies clocks, storage, credentials and capability-limited I/O. Driver/config version should be part of every persisted interpretation. Whether transport framing belongs in a shared library or driver depends on protocol reuse; proprietary polling must not be forced into an ASTM abstraction.

**Verified:** Wasmtime supports WIT/component embedding and fuel/epoch interruption; its documentation distinguishes their execution costs and behavior. Extism exposes a higher-level plugin framework with host controls. Rhai documents safety limits. [Components][wasm-components], [interruption][wasm-limits], [Extism][extism], [Rhai][rhai-safety]

**Inferred — options:** Compiled drivers are simplest initially. WASM components offer typed language-neutral interfaces and isolation but add toolchain/versioning costs. Extism reduces framework work if its ABI fits. Rhai/Lua make mappings easier to edit but need strict API/resource limits and validation. A separately supervised executable with a versioned bounded IPC protocol permits any language and fault containment; it adds packaging, restart and state-recovery work. A subprocess is not a security sandbox without OS restrictions. No release date applies to this architectural option.

**Inferred — recommendation:** Prototype one stateful ASTM driver and one proprietary polling driver before committing to a plugin ABI. Keep deadline-critical ACK/session ownership in trusted host code where practical. Avoid a Rust dynamic-library ABI for independently distributed plugins unless a stable explicit ABI is deliberately maintained. Do not let a driver perform unaudited HTTP delivery or access another driver's state.

## Open questions

1. **Inferred priority:** Obtain licensed LIS01/LIS02 and the current applicable CAP checklist. Public extracts are insufficient to certify full conformance, exact timer requirements or current accreditation wording.
2. **Verified gap:** Only the e 411 vendor-authored host manual (an older revision) was examined in useful detail. **Inferred:** Obtain current firmware-matched documents and permission to publish synthetic protocol fixtures.
3. **Unverified input assumptions:** YHLO iFlash 1200 HL7 2.3.1/MLLP, Autolyser host-polled serial, Biolyte 2000 send-only ASTM and Swelab Lumi HL7/TCP are task context, not independently established driver specifications here. **Inferred:** Confirm exact versions, transport roles, request types, timer/retry limits and directionality with vendors.
4. **Verified limited lead:** The BCI LINK guide 161150-486 describes Literal upload/download modes, while a miniVIDAS document describes a unidirectional literal interface. **Inferred:** Do not extrapolate across VIDAS models/software. Use the Literal specification that matches the installed device (BCI LINK guide 161150-486; the miniVIDAS interface description).
5. **Inferred priority:** Define the receiving-app contract: stable event/command IDs, durable acceptance, per-observation errors, correction linkage, order rejection/cancellation, version negotiation and ambiguous-outcome reconciliation. “Any app over HTTPS” needs this contract plus adapters.
6. **Inferred priority:** Decide maximum offline duration and query-cache freshness. What does each machine do on no order, stale order, cloud outage, expired order or cancellation arriving during execution?
7. **Inferred priority:** Agree clinical ownership: where are unknown tests, orphan results, QC, flags, rerun selection and critical-result notification resolved? The bridge should not accidentally become an autoverification system.
8. **Inferred priority:** Set retention, spool capacity, disk-full behavior, backup encryption/recovery and support access. Decide who responds to an overnight delivery-age alert.
9. **Inferred priority:** Validate real serial adapters/cables, COM identity, baud/parity/flow control, power events, Windows service startup and real analyzer resend behavior. None was tested here.
10. **Inferred priority:** Write the intended purpose and Consult a qualified EU assessment of communication versus accessory/driving functions before promising IVDR exclusion. Revisit when command/control or clinical interpretation changes.
11. **Verified research limitation:** Public operational documentation is much richer for integration engines than proprietary instrument middleware. Internal persistence, plugin SDKs, upgrade rollback and complete config history for Rhapsody/Instrument Manager were not established. **Inferred:** Treat these as procurement questions, not invented implementation facts.
12. **Inferred priority:** Audit Rust candidates against captured de-identified messages and Windows hardware; check licenses, vulnerabilities and maintainer responsiveness before selecting versions. Recent releases and generic HL7 validation do not prove vendor conformance.
