# Analyzer Bridge source research

The Bridge can receive standard ASTM/HL7 results locally and deliver durable FHIR bundles over outbound HTTPS.
It is not a ready-made connector for all five devices: proprietary serial framing and host-initiated polling need Java code.
ASTM TCP host queries get “no orders”; serial host-query replies and HL7 QCK/DSR worklists are missing.
A custom receiver can use HTTPS with Basic credentials as a shared secret without OpenELIS pairing; arbitrary secret headers are not configurable.
Prefer a native Windows Java process for COM ports; retain the Bridge outbox and implement durable, idempotent receipt in the hosted app.

Research date: 2026-11-14. Research only; no build, Docker, tests, analyzer communication, or application changes were executed. Device protocol descriptions below are supplied requirements, not independently verified vendor specifications.

The application packages divide into `connection` (saved configuration/runtime attribution), `profile` (catalog, interpretation), `serial`, `mllp`, `file`, `controller`, `normalizer`, `routing`, `fhir`, `outbox`, `pairing`, `security/config`, `health`, `metrics`, and `store`. [README.md:8–57,77–87](https://github.com/DIGI-UW/openelis-analyzer-bridge/blob/5a3b8a361f873af566bfaae8a549d3b80a4d958e/README.md#L8-L87).

Result flow:

1. TCP ASTM uses `ASTMBridgeAdapter`; MLLP uses `HapiReceivingApplication`; serial uses `SerialPortListener` → `SerialFrameBuffer` → `SerialMessageHandler`; files use `FileWatcher`/`FileMessageHandler`; HTTP uses `AnalyzerInputController`.
2. A `MessageEnvelope` carries protocol, transport, source binding/address, sender hint, raw text, time, listener port and receipt identity. `MessageNormalizer` persists receipt and receipt-time interpretation context; the registry resolves an active saved connection and its pinned profile. Attribution is not authentication.
3. `HttpForwardingRouter` refuses unpersisted input, then `NormalizedBundleRenderer` calls `ASTMResultParser`, `HL7ResultParser`, or `FileResultParser`. It creates delivery bundles and stores them with `outbox.markRendered`. Rendering does not perform network I/O.
4. `OutboxDispatcher` claims persisted deliveries, invokes `FhirDeliveryClient`, and records success/retry/dead-letter state. Analyzer acceptance means locally durable receipt, not clinical acceptance by the remote app.

Evidence: `J/normalizer/MessageNormalizer.java:194–284`; `J/routing/HttpForwardingRouter.java:90–140`; `J/routing/NormalizedBundleRenderer.java:23–30,176–215,268–325`; `J/outbox/FhirDeliveryClient.java:30–33,73–115`. ASTM frame persistence precedes positive ACK (`J/serial/SerialFrameBuffer.java:258–269`); MLLP routing precedes HAPI ACK (`J/mllp/HapiReceivingApplication.java:104–158`).

### HL7 ACK details

The TCP path calls **`return message.generateACK();`**, not an instrument-specific response builder (`J/mllp/HapiReceivingApplication.java:146–158`). It accepts every HAPI-parsable message type (`:184–193`). Successful response: **ACK**, **MSA-1 `AA`**, **MSA-2 original MSH-10**. The source test checks these fields (`src/test/java/org/itech/ahb/mllp/HapiMLLPListenerTest.java:193–234`), but does **not** assert MSH-9.2. Reading the pinned HAPI 2.5.1 dependency resolves that detail: it sets MSH-9.1 to ACK, copies MSH-9.2 from the input, copies MSH-12, reverses sender/receiver and generates a fresh ACK control ID. Thus an ORU^R01 produces **ACK^R01**, with MSA AA and the incoming control ID. For versions at least 2.5 it also fills MSH-9.3=ACK. This is dependency-source evidence, not a tested iFlash exchange. [HAPI AbstractMessage.java:196–222,264–305](https://github.com/hapifhir/hapi-hl7v2/blob/v2.5.1/hapi-base/src/main/java/ca/uhn/hl7v2/model/AbstractMessage.java#L196-L305). Parsing/routing exceptions are delegated to HAPI error handling; there is no vendor QCK/DSR implementation.

Serial HL7 is different: it explicitly builds `MSH|^~\&|BRIDGE|BRIDGE|ANALYZER|ANALYZER|...||ACK|...|P|2.5.1` plus `MSA|AA|<original-control-id>`, wrapped in MLLP. It sends **bare `ACK`**, not `ACK^R01`, and hardcodes 2.5.1 (`J/serial/SerialFrameBuffer.java:313–390`).

### Serial framing and port settings

`SerialFrameBuffer` accepts only `Protocol.ASTM` or `Protocol.HL7` (`:80–98`). ASTM: ENQ→ACK, STX + frame number + payload + ETX/ETB + two hex checksum digits + CR LF; checksum is modulo 256, frame numbers wrap modulo eight, exact duplicate preceding frames are ACKed without appending twice. EOT completes a message only after a final ETX frame. ASTM text is ISO-8859-1. HL7: VT start, FS CR end, UTF-8, durable receipt before MSA AA. Buffer ceiling is 1 MiB (`:24–41,145–308,313–390,438–454`). Shared control characters alone do not establish compatibility with a proprietary serial protocol.

Profile `transport_config["RS-232"]` supplies **all eleven** settings: `default_baud_rate`, `data_bits`, `stop_bits`, `parity`, `flow_control`, `read_timeout_ms`, `message_timeout_ms`, `reconnect_interval_ms`, `max_reconnect_attempts`, `rts_enabled`, `dtr_enabled`. These are read from the pinned profile, not independently configured global serial defaults (`J/connection/SerialConnectionSettings.java:6–36`). Templates use 9600/8/1/NONE/NONE, 1000 ms read, 30000 ms message timeout, 5000 ms reconnect, -1 unlimited reconnect, RTS/DTR true. Stop-bit values 1/2/3 map via jSerialComm (3 represents its 1.5-stop-bit constant), not three physical stop bits.

The saved connection supplies **`values.serialPort`** (`J/connection/BridgeAnalyzerConnectionRuntime.java:299–310`), passed as `portPath` to jSerialComm. Linux examples: `/dev/ttyUSB0`, preferably a stable `/dev/serial/by-id/...` path. On native Windows give `COM3` (example; the actual assigned COM name), not a Linux device path. `SerialPortListener` enforces one connection per path, applies settings, opens the port and installs DATA_AVAILABLE/DISCONNECTED callbacks (`:45–127,196–244`). Windows behavior is an inference from jSerialComm usage, not a tested Windows deployment.

### File and HTTP detail

FILE defaults: 5 s poll, 3 s stability, 20 MiB size bound; source files retained, separate durable state, retries/parked failures. Paths must fall under `bridge.file.importRoots`; mounted network exports are possible if visible to the process. A `position` column is allowed but is not emitted as specimen location (section 8). `configuration.yml:53–75`; `C/analyzer-profile.schema.json:67–103,736–798`; `J/file/FileWatcher.java`, `J/file/FileMessageHandler.java`.

`POST /input` is unauthenticated at Spring Security level but rejects sources without an active HTTP connection **before storage**. It accepts all content types, detects protocol, builds an HTTP envelope and reports durable acceptance. Forwarded source headers are trusted only through configured proxy handling; do not expose this as a general public upload API. `J/controller/AnalyzerInputController.java:95–177`; `configuration.yml:20–24`. This is separate from our app receiving FHIR.

### Concrete interpretation

`templates/astm.json:95–128` illustrates `"testCode":"R.3.4", "call":"R.4.1", "number":"R.4.2"`. ASTM field numbering includes the record type as field 1: R.3 is the third pipe slot (array index 2). HL7 uses HL7 field numbering, with MSH's special separator treatment. These are field selectors inside an already recognized standard message, not parser definitions.

Mindray `src/main/resources/analyzer-profiles/mindray-bc5380.json:1–45` declares HL7 2.3.1, TCP/IP, analyzer initiated, no outbound orders, test code `6690-2` → LOINC `6690-2`, unit `10*9/L`. Its `sample_flags` starts at :489; OBX exclusions at :530; explicit parts at :567; QC rule MSH.11 equals Q at :665–673. Thus the wire code can already be LOINC but remains independently identified as a raw code.

GeneXpert `src/main/resources/analyzer-profiles/cepheid-genexpert-astm.json:48–50,140–160,1239–1290,1414–1422` supplies HIVVL→20447-9, explicit number/call/parts, ERROR/NO RESULT failures, sample flags, and O.12=Q control recognition. Other assays include SARSCOV2→94500-6, FLUA→85477-8, FLUB→85478-6, RSV→85479-4. A quantitative test can have a qualitative call component; “Not detected” is not zero. Run failures become no-value error observations, not reportable answers. QC classification, levels, and matching-rule evidence travel to the receiver; operational QC/lot management does not live in the Bridge. `docs/profile-authoring.md:26–70,87–167` explains these distinctions.

Connection **`values.codeOverrides`** maps _profile code → instrument code_. Inbound is translated back to profile identity; outbound LOINC resolution selects the instrument override. Keys must be declared tests and two assays cannot share a code. `values.numberFormat` can replace decimal separator. These do not justify changing the shared profile for each lab (`docs/profile-authoring.md:156–167`; `J/routing/NormalizedBundleRenderer.java:292–304`). Unknown codes survive as unresolved results rather than receiving invented terminology.

A distribution mounts a **complete** folder and sets:

```yaml
BRIDGE_PROFILE_CATALOG_SHIPPED_PATTERN: "file:/app/analyzer-profiles/**/*.json"
```

This replaces packaged profiles; it does not merge/override them. Copy wanted core profiles unchanged with their IDs; add distribution-owned IDs, not `site.` IDs. Retain every revision used by a saved connection. Site-authored revisions live separately in `BRIDGE_PROFILE_CATALOG_DIRECTORY`. Files have catalog revision/publication metadata; fingerprints are computed, not hand-authored. A missing pinned revision prevents that connection restoring. Editing content under the same revision is allowed by current loader behavior, so pinning revision alone does not freeze bytes; preserve deployed artifacts/digests. `README.md:109–132,194–198`; `docs/profile-authoring.md:169–198`. The guide's opening immutability wording and its later same-revision edit allowance are inconsistent; treat the latter plus runtime behavior as an upgrade risk.

## 4. Parsers and new-protocol integration

ASTM parser walks H/P/O/R/C records, reads accession from O, maintains patient/specimen/QC context, selects R records, extracts result parts, flags and timestamps, and returns `HL7ResultParser.ParsedResults`. Legacy default R code is component four of R.3; value R.4; units R.5. `J/fhir/ASTMResultParser.java:25–35,75–158,262–310`. HL7 parser reads delimiters from MSH, PID, OBR accession, OBX type/code/sub-ID/value/units, NTE comments and SPM context, with configured following/preceeding SPM scope. OBX-2 NM/SN supplies numeric meaning; other calls remain categorical/text. `J/fhir/HL7ResultParser.java:75–186,434–480`; `docs/profile-authoring.md:111–131`. Renderer splits multiple PID groups first, but this is not evidence of arbitrary multi-order/multi-accession correctness (`J/routing/NormalizedBundleRenderer.java:116–173`).

**A profile cannot describe a new fixed-width grammar or VIDAS field-code language.** Allowed protocol variants are ASTM/HL7/FILE; serial framing explicitly rejects others. A pipe-delimited `mtrsl|pi...|ci...` message is not ASTM merely because it uses pipes, nor a CSV table merely because it has delimiters. Profiles can configure CSV columns and standard record selectors, not byte-level negotiation/checksum algorithms.

There is no general runtime-loaded parser plugin SPI. Existing extension seams are:

- Transport lifecycle: `AnalyzerConnectionRuntime` / `BridgeAnalyzerConnectionRuntime`, `SerialConnectionListeners` implemented by `SerialPortListener`.
- Message boundary: `MessageEnvelope` → `MessageNormalizer`, with durable receipt callbacks (`SerialMessageHandler.frameBuffer`, :42–64).
- Parser dispatch: explicit switch in `NormalizedBundleRenderer.renderSegments`, :184–202; reusable result types `FhirBundleBuilder.AnalyzerResult`, `RecordParts`, `HL7ResultParser.ParsedResults`; output `FhirBundleBuilder`.
- ASTM library extension: `L/astm/interpretation/ASTMInterpreter.java`, `ASTMInterpreterFactory.java`; `L/astm/handling/ASTMHandler.java`, `ASTMHandlerService.java`; application `ASTMBridgeAdapter` implements the bridge-side handler. These are ASTM abstractions, not a ready generic proprietary parser system.

Design inference: put a proprietary driver/framer/parser in a small protocol-owned Java package, integrate lifecycle at the connection runtime, persist raw bytes/context before positive acknowledgment, then adapt parsed values to the existing FHIR renderer/outbox. Extending Protocol enum, profile schema/validator, registry and renderer dispatch will be necessary if adding a new first-class protocol. Avoid pretending it is ASTM to bypass those boundaries. An alternative separate local adapter translating to the existing HTTP input keeps the Bridge fork smaller, but requires its own durable serial handling and accurate source binding; it is not supplied functionality.

## 5. Host queries and orders

ASTM TCP: `ASTMBridgeAdapter.java:130–141` calls `AstmHostQuery.noOrdersReply` only after successful handling of a query-only message. It returns a header addressed to the sender plus **`L|1|I`** (“no information”). Q.13=A cancellation gets no response (`J/normalizer/AstmHostQuery.java:8–43,46–58`). Query-only messages are deliberately excluded from result outbox processing (`MessageNormalizer.java:194–202`). The library sends the response on the instrument's existing TCP connection; this is not `/api/orders` or a second HTTP roundtrip to the LIS today.

**Serial caveat:** `SerialMessageHandler.handleMessage` only passes a message to normalizer and returns a boolean/message; `SerialPortListener.java:270–283` only writes framing responses from SerialFrameBuffer. Neither invokes AstmHostQuery nor sends order records. A serial ASTM query gets link-level ACKs, but no application-level no-orders/order reply. Do not transfer the TCP capability claim to cobas serial.

HL7 QRY^Q02: `HapiReceivingApplication.canProcess` returns true for everything, routes through the same result path and generates a generic ACK after durable acceptance. There is no QCK^Q02 or DSR^Q03 builder or query service. A query with no OBX has no deliverable results and can land as PARSE_NO_RESULTS; it is not a worklist exchange (`J/mllp/HapiReceivingApplication.java:104–193`; `J/routing/NormalizedBundleRenderer.java:203–207`).

`POST /api/orders` accepts this JSON (synthetic placeholders):

```json
{
  "connectionId": "saved-connection-id",
  "order": {
    "accessionNumber": "SAMPLE-001",
    "patientId": "PATIENT-001",
    "loincCodes": ["6690-2"]
  }
}
```

It requires connectionId, accession, nonempty LOINC list, active connection, valid outbound host/port, outbound capability. patientId is optional. Resolves LOINC to analyzer codes; returns `unmapped`, dispatches mapped subset (so caller must inspect unmapped even on 200), rejects zero resolved codes. Returns `dispatched` plus connection/protocol, 502 on failed send; no durable outbound order queue is shown (`J/controller/OutboundOrderController.java:49–153`). Authentication: protected management API; Basic with configured `bridge.security` credentials while unpaired, paired peer client certificate thereafter (`J/config/SecurityConfig.java:110–147`; pairing filter). Forward-delivery Basic credentials are a different configuration.

`OrderBuilder.java:23–65`: ASTM H/P/O/L, one `O|seq|accession||^^^code|R` per code, ends L|1|N; HL7 ORM^O01 2.3.1 with PID and ORC/OBR per test, accession in OBR-2/3. It does not build iFlash QCK/DSR. `OutboundAstmClient.java:14–110` opens TCP, 5 s connect, 30 s default reads, ENQ/ACK, framed records, EOT; it uses LIS1-A-style sending, not a serial stream. `OutboundMllpClient.java:14–29,42–125` opens TCP/MLLP and inspects MSA AA/AE/AR; transport failures are retried three attempts with 10 s backoff, deterministic AE/AR are not. **Orders cannot go over serial as implemented.**

### Proposed app order lookup hook (design only)

For analyzer-initiated ASTM queries, replace the unconditional no-orders decision at `ASTMBridgeAdapter` with a connection-scoped `OrderLookup` service. Parse Q specimen/barcode and requested assay codes; call the hosted app over authenticated outbound HTTPS; resolve returned clinical test codes through the saved profile/overrides; return vendor-qualified ASTM order records on the **same analyzer session**. Add an equivalent reply writer to the serial driver, with exclusive port/session ownership and analyzer-specific timeouts. Empty order, lookup failure and uncertain outcome must be distinct; do not report “no orders” on an app outage. For iFlash, intercept QRY before result routing and implement its QCK then DSR conversation and correlation IDs; ORM push is not a substitute.

Our app cannot call the lab's `/api/orders` across NAT. For proactive orders, a local worker would have to poll an outbound HTTPS app endpoint, then dispatch locally; no such cloud-to-local job loop exists here. Local admin/API setup is sufficient for results-only; remote management/pairing as OpenELIS performs it needs reachability or redesign. These are proposed additions, not shipped capability.

## 6. Polling-capable serial drivers

**None found.** Serial scheduling is message timeout checks and reconnect attempts, not periodic analyzer requests (`SerialPortListener.java:121–127,294–338`). The only port writes in receive processing are SerialFrameBuffer responses (:270–272). Declaring `LIS_INITIATED` does not create a polling state machine. Outbound TCP order clients are not result pollers.

Dialab would need a driver owning serial open/close, timer, STX→ACK session establishment, R command, fixed-width decoding, mod-256 checksum, positive/negative responses and EOT. Plug its lifecycle into `SerialConnectionListeners`/`BridgeAnalyzerConnectionRuntime`, its raw receipt into the durable store, and parsed output into the existing result/FHIR path. Use one driver per port, cancel timers on deactivate, distinguish communication failures from an empty result queue, and establish from the vendor specification when acknowledging consumes a result. This is a design sketch, not authorization to build a new driver subsystem.

## 7. Output contract and receiver implementation

### HTTP delivery and authentication

`FhirDeliveryClient.java:74–101,178–181` sends one JSON **FHIR R4 transaction Bundle**, `Content-Type: application/fhir+json`, to **`{org.itech.ahb.forward-http-server.uri}/analyzer/fhir`**. It uses configured base-path resolution, so an app can choose a base under its API. Forwarding health reads **`{uri}/health`** (`README.md:151–158`; `J/health/HTTPForwardServerHealthIndicator.java`). Health and result receipt are different endpoints; the Bridge's own endpoint is `/actuator/health`.

**Plain publicly trusted HTTPS with a shared secret works for a non-OpenELIS receiver without code changes when the secret is the configured Basic password**: configure forwarding username/password and keep the Bridge unpaired. The code falls back to its normal HTTPS client and adds Authorization Basic; no forced pairing gate exists in FhirDeliveryClient. It does not support an arbitrary `X-API-Key` or Bearer setting. The receiver must explicitly implement Basic authentication and the fixed suffix paths. `FhirDeliveryClient.java:81–88,189–212`. Do not confuse this with stock OpenELIS: its current `/analyzer/fhir` accepts only the paired Bridge certificate, rejecting passwords/sessions.

Pairing uses `/pairing`, one-time configured/generated code, durable keypair and SHA-256 peer pins. After pairing the Bridge presents its client certificate and stops sending Basic credentials. `J/pairing/OpenElisClients.java:69–95` creates that TLS client; server trust is the pinned fingerprint **or** configured/JVM trust-store validation. OpenELIS separately pins the Bridge client cert. A TLS-terminating hosted platform must support requesting/validating the client certificate to reproduce this; forwarding an untrusted client-supplied certificate header is not equivalent. Pairing itself is initiated by OpenELIS calling the lab Bridge, so it conflicts with our no-inbound-reachability setup unless performed by a local tool or the protocol is changed.

Receiving-side sources read at OpenELIS commit **`ed3227a7314dfd78e7df45cff650eb47664450f7`**: [AnalyzerFhirImportController.java:36–76](https://github.com/DIGI-UW/OpenELIS-Global-2/blob/ed3227a7314dfd78e7df45cff650eb47664450f7/src/main/java/org/openelisglobal/analyzerimport/action/AnalyzerFhirImportController.java#L36-L76), [pairing guide:1–82](https://github.com/DIGI-UW/OpenELIS-Global-2/blob/ed3227a7314dfd78e7df45cff650eb47664450f7/docs/analyzers/bridge-pairing.md#L1-L82), [analyzer spec](https://github.com/DIGI-UW/OpenELIS-Global-2/blob/ed3227a7314dfd78e7df45cff650eb47664450f7/specs/analyzers/spec.md). ### Outbox, retries and deduplication

SQLite outbox uses WAL and **synchronous FULL** (`J/outbox/SqliteOutboxStore.java:27–28,70–83`; `J/store/SqliteSupport.java:154–163`). Persist on disk, not JVM temp. Retain raw receipt, selected interpretation context and rendered bundles. Delivery retry does not reinterpret under today's profile. Defaults: dispatcher safety poll 1 s (also explicitly woken), lease 120 s; forwarding connect/read 30 s each; **150 attempts**, base **5 s**, multiplier **2**, nominal cap **10 minutes**, jitter **0.2**. Jitter is applied after capping, so capped retries range about **8–12 minutes**, not an absolute ten-minute ceiling (`J/outbox/BackoffPolicy.java:40–49`). Delivered retention unlimited unless configured; dismissed dead letters 90 days; undismissed dead letters retained. `configuration.yml:77–100`; `README.md:151–173`. File read/processing retries are a separate queue/state policy.

Any **2xx** means delivered, regardless of JSON `success` field. No network/TLS response, 408, 429 and 5xx retry; redirects dead-letter (no follow), 422 configuration dead-letter, other 4xx rejection dead-letter. `J/outbox/DeliveryOutcomeClassifier.java:14–44`. Return no 2xx until durable receipt; a login page answering 200 would lose the Bridge's retry protection.

Delivery IDs are `astm-v1:`, `hl7-v1:`, `file-v1:` plus SHA-256 over length-prefixed connection ID, content hash, accession (`DeliveryIdentity.java:24–28,66–95`). Text content hash is UTF-8; FILE hash uses bytes. HL7 multi-PID grouping hashes each group with header (`NormalizedBundleRenderer.java:150–164`). Repeated identical input on the same connection/identity deduplicates, including after restart; distinct bytes can give another delivery even for the same measured value. This is delivery dedupe, not proof that two analyzer runs are the same clinical run. Resource UUIDs and file path are not dedupe keys.

### What our receiver must implement

1. Authenticated HTTPS POST at base/analyzer/fhir accepting application/fhir+json; GET base/health returning exactly HTTP 200 for forwarding health (its body is not interpreted). Health uses the same Basic or paired client configuration; `J/health/HTTPForwardServerHealthIndicator.java:83–106`. Basic password authentication is the smallest available outbound-only configuration; pairing/mTLS requires additional infrastructure/protocol work.
2. Validate supported contract versions, Bundle shape, authoritative connection identity, per-entry references, typed result values and classification. This is a custom ingestion contract, not a requirement to expose a general FHIR server executing arbitrary transaction entries.
3. Atomically persist a delivery receipt keyed by connection/message identity together with its raw bundle and staged results. Repeat an accepted delivery returns success and the same receipt, with no duplicate results/QC. Commit first, then respond 200. Do not treat generated resource UUIDs as stable IDs.
4. Map profile test/sub-identity/canonical answer to local tests, preserve units/comparators, separate SAMPLE_FLAG/CONTROL/PATIENT and SETUP/ROUTINE, retain failures and unresolved identities for explicit review. Never silently attach position-only/unknown sample output to a patient.
5. Return transient 5xx/429 only for retryable failures; meaningful 400/422 for operator-correctable problems. Stock OpenELIS responds `{success:true,receiptId,analyzerId,resultsStaged,resultsHeld,controlResultsProcessed}`; Bridge currently relies on status alone, so a smaller response can work. Use equivalent durable semantics rather than merely mimicking JSON.

These are a design sketch for a receiver, not app implementation. Stock controller parsing/status behavior: OpenELIS `AnalyzerFhirImportController.java:36–76`; receipt semantics: `C/README.md:178–194`.

## 8. Sample identity and position-only reports

The normalized result model is `ParsedResults(accessionNumber,results,patient,specimenDescriptor,sampleFlags)`, not a tube/rack model (`HL7ResultParser.java:529–550`). ASTM extracts the first component of O's specimen field: `O|1|BARCODE^LOCATION` yields **BARCODE**, discarding LOCATION (`ASTMResultParser.java:262–276`). O/R sequence counters are not specimen identity. HL7 prefers OBR-3, falls back to OBR-2, retaining the field text; it does not derive rack/cup fields (`HL7ResultParser.java:434–449`). Missing accession falls back to HL7-UNKNOWN; ASTM fallback code exists but ordinary records without accession are skipped (:132–158), so missing identity is not guaranteed to deliver a useful result.

FILE schema permits a `position` column, but `ParsedResults`, `AnalyzerResult`, `RecordParts` and `FhirBundleBuilder` have no output position/container/rack/cup/sequence slot. No Specimen.container emission exists (`FhirBundleBuilder.java:339–343,645–655`). `specimenPosition` is SPM placement in the HL7 message, **not** physical location.

If a device sends only a location in the field treated as sample ID, the receiver gets that string as Specimen.identifier.value, without proof it is a barcode. If location is elsewhere, it is generally absent from normalized FHIR (raw receipt remains local). A proprietary protocol cannot reach even that stage without a parser. A rack/cup-only integration needs an explicit ordered-run/position-to-sample binding and location-preserving output change; inferring a patient from “position 3” is unsafe. This is a required design decision if actual device documentation reveals position-only identification.

## 9. Deployment on a lab Windows PC

**Recommended starting point (inference): native Java 21 JAR with physical/USB serial ports**, if the lab PC is the selected host. Build elsewhere, deploy the reviewed artifact, run `java -jar ... --spring.config.location=...` under a Windows service supervisor configured to start/restart with the machine. The repo supplies the Java application, not a complete Windows installer/service setup. Set writable Windows absolute paths for all durable directories and COM names; verify real RS-232 cable wiring, parity, baud and device settings from manuals.

Docker Desktop is reasonable for TCP/file-only connections, but Linux-container `devices: /dev/ttyUSB0:/dev/ttyUSB0` is a **Linux** mapping, not a way to map host Windows COM3. Docker documents no direct USB passthrough; USB/IP is a separate workaround with backend/device limitations, not guaranteed compatibility. Prefer native JAR; alternatives are a Linux mini-PC with USB serial mapped normally, or a qualified serial-to-TCP gateway/local relay. A gateway preserves proprietary bytes but does not add a missing parser/poller or serial host-query implementation. [Docker Desktop FAQ](https://docs.docker.com/desktop/troubleshoot-and-support/faqs/general/), [USB/IP documentation](https://docs.docker.com/desktop/features/usbip/).
